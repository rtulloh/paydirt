## Description

`get_play_type_from_key` and `get_defense_type_from_key` in the web backend
default unknown inputs to line plunge and standard defense. Thus an invalid
nonempty offensive or defensive call sent to `/api/game/execute` can advance
the game using a play the client did not request. The same helpers are used
for two-point tries. `test_play_modifiers.py::test_invalid_play_string`
explicitly expects the fallback, so this behavior is currently covered but
does not protect against accidental game mutation from malformed calls.

## Resolution / verification

The backend validates player and supplied CPU calls before choosing a play or
mutating game state. Unknown keys, empty strings and unsupported suffixes return
HTTP 400; valid case-insensitive calls and previously supported modifier
combinations still work. Two-point requests use the same key validation.
The new public-sample API tests cover both possession sides, invalid CPU calls,
fourth-down AI selection, two-point calls, unchanged state and valid mappings.

`test_play_modifiers.py::test_invalid_play_string` now expects rejection: its
old success expectation encoded the undesired line-plunge fallback. The
`test_api.py::test_execute_play` fixture now chooses an offense or defense key
according to possession; its former unconditional `1` was invalid when the
human was on defense and succeeded only through the standard-defense fallback.
